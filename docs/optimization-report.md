# 识别与纪要优化报告

基线提交是 `db2aef0`（「基线：导入原始代码」）。之后按功能分成四次提交，本报告单独一次。补丁在 `artifacts/patches/`，对应从基线到本报告（不含再后面的「导出补丁」提交）。

这次没有新增第三方包。Nemotron 3 用的是锁文件里已有的 `transformers 5.20.2`（里面已经带 `nemotron3_diarization`）。`pyproject.toml` 和 `uv.lock` 没有改。

## 环境

单元测试跑在这台 Linux x86_64 上：Python 3.11.18，CPU 版 torch 2.14.1+cpu。没有 GPU。

公开会议录音不在这台机器上。`uploads/asr-eval.tgz` 里只有空的虚拟环境残留，没有评测脚本、标注或分数。因此下面**没有**新的 AISHELL-4 / AliMeeting DER 或字错率。任务里列出的那些数字仍是待验证的假设，这里没有复现，也不当作结论。

打分器只做了自检，不是语料结果：

- `tests/audio/cer.py` 的编辑距离：同一段文字错字为 0；删掉 1 个字则漏字为 1。
- 已随 `pyannote-audio` 装上的 `pyannote.metrics` 4.x：两份相同标注 DER = 0；把 20 秒里的两个人并成一个人，DER = 0.5000（collar 默认，含重叠）。

## 1. 双路录音

**改了什么。** 选「麦克风 + 电脑声音」时，两路各自采集，按 100ms 交错成双声道 PCM 上传（左：麦克风，右：电脑声音）。会后两路分开转写、分开做说话人区分，再按时间合并。两路同时说**不同**的话都保留；文字几乎一样、时间又重叠的，当成串音，只留更响的那路。麦克风上说得最久的人默认叫「我」，电脑声音只有一个人时叫「对方」。已经起过的名字不会被覆盖。

只录麦克风、上传文件、手机当麦克风、全天模式仍是单声道，块大小仍是 3200 字节。同一场会如果已经用一种来源录过，续录必须用同一种来源。

**怎么验证的。** `tests/test_dual_audio.py`，以及原有的平台、聚类、拆句、词库等单元测试。没有近场双声道会议录音，所以没有「混成一路」对「分两路」的字错率对比。

**风险。** 串音判定靠文字相似和音量，两个人恰好说同一句话时会丢掉较轻的一路。电脑声音断开后，那一路先补静音，避免整段录音卡住，但断开期间对方的话会丢。浏览器必须在共享时勾选系统音频。

## 2. 会议上下文热词

**改了什么。** 识别前把这些词按优先级合并，最多 30 个：本场额外热词、常用词库、参会人姓名、手写标题和笔记里的专名、以往会议里至少出现过两次的专名。互相包含的说法只留更长的（「长尾词」留下，「长尾」去掉）。

Fun-ASR-Nano 和 Paraformer 把这 30 个词当热词。豆包接口不接受热词，转写后再用原来的「读音像热词、又不是常用词」条件改字（例如「陈伟驰」→「长尾词」），「预算是」这种常用词不改。

**怎么验证的。** `tests/test_context_hotwords.py`、`tests/test_vocab_names.py`。没有在公开语料上重跑字错率，所以不能声称专名识别变好了多少。

**风险。** 30 个上限仍然可能让 Nano 在听不清的地方硬塞热词；原有的 CTC 核对还在，对不上就丢掉热词再认一次。历史专名来自本机已有转写，第一场会没有历史。豆包的转写后纠错只覆盖 3–8 个汉字的热词。

## 3. 可选的 Nemotron 3 说话人区分

**改了什么。** 设置里的「区分说话人」多了一项「Nemotron 3」。选中后，会后转写用子进程跑 `nvidia/Nemotron-3-Diarization`（约 100M 参数，OpenMDW-1.1）。模型第一次使用时从 Hugging Face 下载，大约 400MB。设备顺序是 CUDA、Apple MPS、CPU，使用 float32。失败就退回 CAM++。

默认仍是 CAM++。没有在近场或会议录音上证明它更好，所以没有改默认。它的训练数据包含 AISHELL-4 train，就算以后在 AISHELL-4 test 上更好，也不能直接当成近场周会的结论。

重叠：Nemotron 可以在同一时刻给出两个人。这时按逐字时间把一句话切开，重叠的那段标上多个人（转写里显示成「说话人A、说话人B」）。没有重叠时，拆句逻辑和原来一样。短于 200ms 的说话人段丢掉。用户填了人数时，只留说得最久的那么多人。

**怎么验证的。** `tests/test_diar_overlap.py` 用假的帧级概率和逐字时间，不下载模型。`tests/test_split_level.py` 确认默认仍是 `campp`，设置成 `nemotron` 会生效，未知值退回 `campp`。

**没有的数字。** 没有跑 AISHELL-4 或 AliMeeting，所以没有新的 DER，也不能确认「5/6 对 0/6」或「7.64% 对 24.06%」。那些数字维持原样，当作未在本次复核的假设。

**风险。** 最多 8 个人。概率阈值用的是 0.5，不是 NVIDIA 评测脚本里的后处理，和模型卡上的 DER 不能直接比。MPS 上如果某个算子不支持，子进程会改到 CPU，会慢。第一次需要能访问 Hugging Face。

## 4. 纪要确定性校验

**改了什么。** 生成纪要不再直接收 Markdown。顺序是：

1. 模型只输出 JSON（标题、概要、各节、待办、关键词）。待办每条带事项、负责人、期限、时间戳和一段要求逐字摘自转写的原话。
2. 代码核对。期限必须在对得上的原话里出现，否则改成「待定（原文未说明期限）」。只出现「周四」不能写成「下周四」或「周四全天」。负责人必须是转写正文里出现的姓名，否则改成「待定（原文未点名）」。「我」「说话人1」不算。时间戳如果和原话所在的段落对不上，就改到那段的起点并注明「已按原话校正」；完全对不上的标「时间对不上」。
3. 再用模板把核对后的结构渲染成 Markdown。页面上如果有改动，会提示改了几处。

长会议仍先分段提炼，再让模型出 JSON。提炼提示要求用引号留下原话，但核对只认转写正文。原话在摘要里被改写过的期限，会被改成待定。

**怎么验证的。** `tests/test_minutes_check.py` 用固定转写，不调用模型。覆盖了「下周」没有原话、原话里真有「下周」、「周四全天」不能从「周四开始、周六全天」推出来、摘句能把时间从 00:10 校正到 02:00、坏 JSON 会报错。

**风险。** 只核对期限、负责人和时间戳，不核对「价差 21%」这类编造的数字。模型可以把期限写进概要正文而不放进待办表，正文里的期限不会被改成待定，只有 `[mm:ss]` 会被检查。摘句至少 4 个字才算对上；对不上时退回到时间点前后 90 秒，这段窗口里如果碰巧说过「下周」，可能放过一条其实不相关的待办。

## 顺带做的一件小事

词库缓存在写入后仍按文件修改时间判断要不要重读。这台环境里 `os.replace` 不更新修改时间，测试会读到旧词库。`vocab.save` 现在写入后直接更新缓存。这不改变识别结果，只是让新规则马上生效。放在热词那次提交里。

## 在 Mac 上要做什么

机器是 Apple Silicon 时，按原来的方式启动即可（`./start.sh`）。不需要为这次改动重装依赖。

1. **线上会议分路录音。** 新建会议时音频来源选「麦克风 + 电脑声音」。浏览器弹出共享时选整个屏幕或标签页，并勾选共享音频。录音页会把两路分开显示成「我」和「对方」。会后精转会替换成更细的说话人。线下会议仍选「麦克风」。手机、平板的浏览器没有系统音频，这一项保持灰色，手机录音不受影响。
2. **热词。** 不用新开关。常用词库、本场热词、参会人、标题、笔记和以往会议里的专名会自动合并，最多 30 个。首页输入框下面有说明。
3. **Nemotron 3。** 打开设置，在「区分说话人」里选择「Nemotron 3」。默认不要改，仍用「标准」。第一次会后转写需要联网，从 Hugging Face 下载约 400MB。下载失败会自动退回标准方式，转写不会因此中断。已有录音要点「重新转写」才会用新的区分方式。
4. **纪要。** 还是在纪要页点生成。待办表里没有原话的期限会写成「待定（原文未说明期限）」，没有点名的负责人写成「待定（原文未点名）」。改过的条目会出现在页面上方的提示里。需要大模型接口，和原来一样。
