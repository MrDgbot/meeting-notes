# 改进记录：已知短板修复（2026-10-26 起）

只用公开数据（AliMeeting）。规矩和以前一样：先写方案和判定标准，再看结果；开发集上可以反复试，留出集只在全部改动定下来以后跑一次。中途改了方案的，写在文末“偏离”里。

## 数据、基线、打分

- 开发集：AliMeeting Eval 8 场、4.2 小时。选方案、定参数都只看它。
- 留出集：AliMeeting Test 20 场、10.8 小时。全部改动定下来以后，整套流程只跑一次，和基线比，不再回头调。
- 基线：当前公开版本。Test 上字错率 32.1%（2 人会议 8.8%），人数判对 13/20，DER（collar 0.25）27.3%。开发集基线用当前代码重跑一遍（`r1-eval-off`），和改动在同一份代码上比。
- 打分：`tests/eval/score.py`（字错率 sclite / jiwer，DER dscore / pyannote，谁说了什么 cpCER 用 MeetEval）；人数照 `spk_score.py` 的数法（过一遍 `_speaker_units` 后剩下的说话人）。

## 动手前已经看过的东西（如实列出）

- Test 上的错字按“参考片段和别人重叠的比例”分组：单人说话的片段占 29% 的字，字错率 7.5%；以重叠为主的片段占 31% 的字，却贡献了 65% 的错字。
- Test 上 3 人会议在单人说话时也漏字：R8008_M8015 里有一个人单独说话的部分 91% 没识别出来。他的音量中位数 -55.9 dBFS，VAD 只覆盖到 5%；2 人会议的人在 -31 到 -41 dBFS。
- 开发集上只跑 VAD 比了几种做法（参考语音被 VAD 覆盖的比例 / 误报）：现状 90.7% / 3.9%；整段按 RMS 放大到 -30 dBFS 97.2% / 4.4%；ffmpeg dynaudnorm 97.8% / 4.6%；修掉“灵敏度不生效”后阈值 0.4 是 91.1% / 3.9%。所以第 1 项的方向是在开发集上看过 VAD 结果之后定的，完整流程的字错率还没看过。

## 各项方案和判定标准

### 1. 声音小的人被漏掉：转写前音量归一

整段音频按 RMS 放大到 -30 dBFS（只放大，最多 +30 dB，0.8 以上软限幅）。两种用法：
A `vad`：只给语音检测用，识别和声纹仍用原始音频；B `all`：都用放大后的。

- 开发集上 A、B 都跑完整流程，选总字错率低的。
- 采用条件：开发集总字错率比基线降 ≥1 个百分点；2 人会议字错率变差不超过 0.3 个百分点；DER（collar 0.25）变差不超过 0.5 个百分点。

### 2. “谁说了什么”错得多：按说话人拆句

现在是先识别一大段，再按整句定说话人；一句话里换了人，整句也只归给一个人。方案：用 Nano 的逐字时间戳给每个字标上声纹聚类得到的说话人，换人的地方把句子切开（换过去的人要连续够长才切，阈值在开发集上选）。只改文字归给谁，不改识别出的文字和说话人时间段，所以字错率、DER 不变。

- 指标：cpCER（MeetEval）。
- 采用条件：开发集 cpCER 降 ≥2 个百分点。达不到时再试“先按说话人切单元、每个单元单独识别”（云端识别现在就是这样做的），同样的条件。

### 3. 抢话漏字：重叠检测 + 语音分离（限时实验）

先调研现成可用的模型（许可证、是否要登录才能下载、能不能在 Apple Silicon 上跑），选 1–2 个组合，在开发集上试：检测出重叠的地方，把声音分成两路，第二路单独识别后补进转写稿。

- 采用条件：开发集上 3–4 人会议的字错率降 ≥3 个百分点；2 人会议变差不超过 0.5 个百分点；处理时间不超过现在的 2 倍。
- 限时：达不到就不并进产品，在 README 里如实写“试过、没成”，留着实验脚本。

### 4. 4 人会议人数判少

在缓存的声纹上离线试：换声纹模型、改聚类做法；如果第 3 项有可用的重叠检测，再试聚类时剔除重叠处的声纹块。

- 指标：开发集上人数判对场数、平均人数误差、DER（collar 0.25）。
- 采用条件：开发集平均人数误差下降，DER 变差不超过 0.5 个百分点。开发集只有 8 场，容易过拟合：参数只在少数几个候选里选，不做细扫。

### 5. 只支持 macOS

不是算法问题，按功能验证：Linux 在 Docker 里端到端跑通（上传转写、全天模式从 PulseAudio 收音）；Windows 没有真机，在 GitHub Actions 上跑单元测试和一次端到端转写。没验证到的写明。

## 留出集

开发集上定下全部改动后，Test 整套跑一次，和基线比，数字照实写进 README。某个主指标（字错率、cpCER、DER、人数）比基线差的，记为偏离、在 README 写明，不在 Test 上换方案重测。

## 结果

### 开发集（AliMeeting Eval 8 场）

第 1 项，完整流程（`r1-eval-{off,vad,all}`，同一份代码，只差音量归一的开关）：

| | 总字错率 | 2 人 | 3 人 | 4 人 | DER c0.25 | cpCER | 漏 / 替换 / 多（字） |
|---|---|---|---|---|---|---|---|
| 现状 off | 32.55% | 13.04% | 54.63% | 38.85% | 27.79% | 52.26% | 21127 / 4393 / 871 |
| A vad | 29.85% | 13.00% | 25.32% | 39.80% | 23.48% | 51.17% | 17140 / 6037 / 1029 |
| B all | **29.76%** | 13.02% | 26.19% | 39.47% | **23.17%** | 50.79% | 17059 / 6033 / 1040 |

A、B 都达到采用条件（总字错率降 2.8 个百分点，2 人会议不变）；按事先的规则选字错率低的 B。
小声的那场（R8008_M8013，整体要放大 19 dB）从 54.6% 降到 26.2%。也有一场变差：R8001_M8004 从 44.4% 到 49.5%，
漏字少了 1061 个、认错的字多了 1536 个：多认出来的主要是抢话时的背景人声，认得不准。

第 2 项（`split_sweep.py`，在 B 的输出上离线算；min-ms 0 和产品输出逐段一致）：

| cpCER | 不拆 | 500 ms | 1000 ms | 2000 ms | 3000 ms |
|---|---|---|---|---|---|
| CAM++ 的说话人时间段 | 50.79% | 44.84% | **44.83%** | 46.40% | 47.45% |
| pyannote 的说话人时间段 | 42.69% | 35.32% | 35.76% | 37.51% | 38.43% |

采用 1000 ms：降 6.0 个百分点，达到条件（≥2）。500 ms 是看到 1000 ms 在候选边上以后补测的，差别在 0.5 个百分点以内、段落多 10%，取 1000 ms（偏离 D2）。

第 3 项（重叠，可行性探针）：从开发集参考里挑出 20 处两人真重叠、附近没有第三个人的片段（745 字），比较三种做法的字错率：

| 做法 | 字错率 |
|---|---|
| 只识别混合音（现状） | **38.7%** |
| sepformer-whamr16k 分成两路，两路都识别 | 53.7% |
| MossFormer2_SS_16K 分成两路，两路都识别 | 49.8% |
| MossFormer2：混合音 + 补一路（事后挑最好的那路，实际做不到） | 44.4% |

分离以后反而更差：分出来的每一路都带着对方的残声和失真，Nano 认错得多；而 Nano 在混合音上本来就能认出两个人的一部分话。
有几处分离效果很好（61% → 6%），但没有可靠的办法事先判断哪处该用，20 处样本上调选择规则只会过拟合。按事先的规矩，第 3 项不并进产品。

第 4 项：现成的 pyannote community-1（`pyannote-community/speaker-diarization-community-1`，CC-BY-4.0，不用登录就能下载；ModelScope 上有逐字节相同的镜像）自带重叠检测和 VBx 聚类：

| | 开发集 DER c0.25 | 人数判对 | 平均人数误差 | 真实周会 DER c0.25 | 周会人数（参考 6） |
|---|---|---|---|---|---|
| 现状 CAM++（音量归一后） | 23.17% | 5/8 | 0.625 | **20.9%** | **6** |
| pyannote | 16.86% | 6/8 | 0.250 | 51.5% | 7 |
| pyannote + CAM++ 合并 0.72 | 18.22% | 6/8 | 0.375 | 37.5% | 4 |
| pyannote + CAM++ 合并 0.78 | **15.82%** | **7/8** | **0.125** | 24.8% | 5 |

真实周会：一场 95 分钟的内部周会，6 人，笔记本电脑近场录音；参考说话人取自一款商用会议记录产品的逐字稿（句子级时间，没有重叠）。只用来看说话人，不公开内容。
pyannote 在 AliMeeting（会议室远场）上明显更好，但在这场近场周会上把说得最多的那个人（约 2300 秒）拆成了两个人（1181 + 1004 秒），认错人从 1.6% 涨到 36%。
用 CAM++ 声纹把太像的说话人并起来能救回一部分，但都不如现状。产品的主要用法更接近这场周会，所以：

- 默认仍用 CAM++；
- pyannote + 合并 0.78 做成设置里的可选项“会议室远场”，给多人围坐、离麦克风远的会议室录音用（偏离 D3）。

隐私：pyannote 默认会把用法统计（音频时长、人数、会话 id，不含音频）发到 otel.pyannote.ai。产品在子进程里导入前强制关掉，模型只从本地目录加载；
`tests/test_diarize_offline.py` 把网络连接函数全换成报错后跑一遍，确认一次连接都不发起。

顺带核对了打分流程：pyannote 公布的 community-1 在 AliMeeting 第 1 路上 DER 20.3%（collar 0、含重叠，Test 集）；我们用自己的参考答案和打分器在 Eval 上测得 20.48%，量级一致。

离线模拟和产品代码一致：用产品代码（`run_pipeline.py --diarizer pyannote`）在开发集上跑了 3 场，和离线模拟（同样的 Nano 输出 + pyannote 时间段 + 合并 0.78 + 拆句 1000 ms）逐段比，文字、说话人、段落、时间段全部相同（162/162、163/163、247/247 段）。为了让出 GPU 给留出集，剩下 5 场没跑。

新默认（音量归一 + CAM++ + 拆句 1000 ms）在真实周会上也跑了一遍：这场录音够响，音量归一不起作用（放大不到 0.5 dB，原样返回），说话人结果和上一版完全相同（DER 20.9%，6 人）；
拆句后段落从 228 段变成 267 段，以那款商用产品的逐字稿为参考，cpCER 从 24.48% 降到 23.81%，没有变差。

## 偏离

- D1（第 4 项候选扩大）：写方案时只列了“换声纹模型、改聚类、剔除重叠处的声纹块”。之后查到 pyannote community-1 有不用登录的镜像，就把整套 pyannote 也列为候选（它同时换了声纹模型、聚类和重叠处理）。
- D2（第 2 项多测了一个点）：1000 ms 在原候选（1000/2000/3000）的边上，补测了 500 ms；差别在 0.5 个百分点以内，按段落更少取 1000 ms。
- D3（第 4 项加了真实周会这道检查）：写方案时漏写了“真实周会上不能变差”，上一轮（说话人聚类）就是这样做的。pyannote 在开发集上过了原定条件，但在周会上明显变差，所以没有设为默认，改成可选项。合并阈值 0.78 是在开发集 + 周会上从 0.66 / 0.72 / 0.78 里选的。
- D4（留出集的跑法）：最初定稿时把 pyannote 设成了默认、并已开始跑 Test；看到周会结果后停掉，那一次的输出一份都没看就删了。之后按新的定稿（默认 CAM++；可选 pyannote + 合并 0.78）重新开跑，两种模式各跑一次。
- D5（留出集上人数变差）：第 1 项的采用条件只看了字错率和 DER，没有把人数列进去；开发集上人数也确实没变。Test 上默认模式的人数判对从 13/20 降到 9/20。按事先的规矩，不在 Test 上换方案重测，照实写进 README；
  会议室录音建议用“会议室远场”模式（17/20），知道人数时手动填上。要改善默认模式的人数，下一轮应该把人数列进采用条件，在开发集上重新选（比如音量归一后对 CAM++ 的小簇合并做调整）。

## 其他几项（这一轮做完的）

### 憨包云端识别时热词不起作用

- 憨包这个接口不接受热词：在开始会话的参数里试了 5 种常见写法（`corpus.context`、`context` 两种格式、`hotwords`、`extra.hotwords`），4 段含“长尾词”的录音识别结果和不传完全一样。所以热词只在憨包没出字、改用本机补识别时才用得上。
- 那场 95 分钟周会里，飞书逐字稿有 18 处“长尾词”，憨包认对 12 处；认错的有“陈伟驰”“常伟奇”“常玩”“什么词”等。把句子单独剪出来发，憨包能认对，所以错是在长段里出的，不是不认识这个词。
- 做法：转写页面提示“可能认错的热词”（`vocab.suspects`），一键加成纠错规则，不自动改。条件和检验见 `vocab.py` 和 `tests/eval/hotword_suspects.py`：
  那场周会配 20 个业务热词，报出 3 处（陈伟驰、常伟奇 → 长尾词，你不说图 → 以图搜图），对照飞书和上下文都是真的认错了；
  AliMeeting 15 小时转写配同样 20 个热词，一处都没误报。“常玩”“什么词”这类读音差太远、或者本身是常用词的，找不到。
- 纪要提示词里也写明了“读音像热词、上下文说不通的，多半是热词认错了”。

|---|---|---|---|---|---|
| 原提示词 · 通用模板 · 思考 | 28.0（26–30） | 0.5 | 1.0 | 89 秒 | 50–89 秒 |
| A 新提示词 · 通用模板 · 思考 | 26.7（24–29） | 0 | 0 | 74 秒 | 52 秒 |
| B 新提示词 · 周会模板 · 思考 | 24.0（23–25） | 0 | 0 | 73 秒 | 59 秒 |
| **C 新提示词 · 通用模板 · 关掉思考** | **29.0（27–30）** | 0.3 | 0 | **30 秒** | **3 秒** |
| D 新提示词 · 通用模板 · 思考强度 low | 28.7（27–30） | 0 | 0.7 | 69 秒 | 49 秒 |

- 新提示词加了三条：数字照抄、不改成范围；每个时间单独一对方括号；读音像热词的按热词写。
- 判定（跑之前定的，没有提前写进文件）：要点平均不比基线少 1 条以上，错误不比基线多，才采用；思考设置要省 30% 以上的时间。
  A 单看要点少了 1.3 条（各次 24–29，波动很大），没过线；C（新提示词 + 关掉思考）要点和错误都不比基线差、快 3 倍，采用 C。
- 周会模板（B）反而少写了要点：它按人分组，漏掉了按议题记下的细节。所以没有做“自动判断会议类型选模板”。
- 思考强度 low 几乎不省时间。在一场 15 分钟的会上抽查：关掉思考 12 秒，开着 54–78 秒，时间戳、发言人都没错。
- 只有一场会、每组 3 次，结论很粗；“要点”清单来自同一场会的飞书纪要，有过拟合这场会的风险。
- 关掉思考是接口级的设置（“额外请求参数” `{"reasoning": {"enabled": false}}`，只对支持它的接口有效）。开着思考的模型，页面上会显示“正在思考，已 N 秒”。

### 说话人 5 有 22% 被算到说话人 1：查了，没改

- 原以为是憨包那条路把 2 秒以下的短发言并进了相邻的人（`_speaker_units` 的 `min_turn`）。用飞书逐字稿对照：聚类出来的原始时间段里，飞书说话人 5 就只有 80.6% 对得上；
  并短发言以后整体一致率反而从 96.5% 升到 97.4%，`min_turn` 降到 1000 / 500 / 0 都更差。所以不是这个原因。
- 对不上的 35 秒里，声纹小块一半离说话人 1 更近、一半离说话人 5 更近，相似度都在两人之间（0.55 / 0.54，两人各自的一致处是 0.62 / 0.68）：多半是两人交替很快、互相插话的地方，也可能是飞书自己标错了。没有可靠的改法，不改。

### 推测说话人姓名

- 转写页“推测姓名”：让模型从转写里找自我介绍、“某某你说一下”之后开口的人这类直接线索。
- 服务端逐字核对模型给的原话（必须在它说的时间前后 90 秒内出现），并且至少要有一句是这个人自己说的；核对不上的丢掉。只给建议，用户勾选后才改名。
- 那场周会上推测出两个人名，各带两句原话（主持人点到一个人负责的事，随后这个编号说“等一下我汇报”之类）。没有标准答案，要用户确认。
  第一版没有“本人说过一句”这条，模型把“跟某某说的”这种别人的转述也当成了线索，加上以后去掉了。

### 抢话漏字：又试了三种做法，都没成

还是第一轮那 20 处两人真重叠的片段（开发集，745 字），基线（只识别混合音）38.7%；Nano 在 MPS 上每次结果略有不同，复测三次 38.1–38.7%，±0.5 个百分点以内算噪声。
脚本 `tests/eval/overlap/round2_*.py`，各自的环境在 `tests/eval/.venv-saasr`、`.venv-tse`。

| 做法 | 字错率 | 耗时（114 秒音频） |
|---|---|---|
| 只识别混合音（现状） | **38.7%** | 7.7 秒 |
| 按说话人时间段裁窗口再识别（参考时间段 / pyannote 时间段） | 39.2% / 39.1% | 约 11.5 秒 |
| SA-ASR（M2MeT 2.0 的基线，在 AliMeeting Train 上训练，Apache-2.0） | 49.4% | CPU 约 90 秒 |
| 目标说话人提取 REAL-TSE BSRNN + Nano（参考登记音 / pyannote 登记音） | 70.6% / 63.5% | 约 22 秒 + 两路识别 |

- 裁窗口：很多片段里有一个人的话盖满整个窗口，裁出来还是混合音。
- SA-ASR 有领域内的优势（同一个数据集训练，还拿 Eval 做过验证），但本身认字能力弱。
- 目标说话人提取：声纹本身分得开（同一人余弦 0.81，不同人约 0.3），但在这批会议录音上提取后音质反而变差（人为 0 dB 混合时 SI-SDR 降 2 dB），两路认出来的基本都是声音大的那个人。模型是在干净的英文合成数据上训练的，和第一轮分离模型的问题一样。
- 结论：单路麦克风、用现成模型，这条路目前走不通。还值得等的：认字能力强、又在真实中文会议重叠上训练的多人识别模型（目前公开的没有）；或者用多路麦克风做空间提取（要换掉产品单麦克风的前提）。

### 短录音的人数（重新转写全天模式的几段录音时发现，先写方案再看结果）

重新转写 9 段全天模式录音时，1–2 分钟的几段都从 2–3 人变成了 1 人。原因在 `SPK_MIN_SEC = 30`（上一轮 D5 定的）：总时长不到 30 秒的说话人会被并进别人，而一两分钟的录音里，除了说得最多的那个人，谁都凑不够 30 秒。这个阈值是在 15–35 分钟的会议上选的。

- 数据：从开发集每场录音里随机取 1 / 2 / 4 分钟的窗口各 3 个（固定种子），AliMeeting Eval 8 场 + AISHELL-4 train_L 30 场；只用窗口内的声纹小块重新聚类。参考人数 = 窗口里说话够 3 秒的人。
